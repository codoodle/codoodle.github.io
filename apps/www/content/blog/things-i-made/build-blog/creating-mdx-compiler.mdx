콘텐츠 관리를 텍스트 기반의 단순함과 유연성이 장점인 마크다운을 사용하기로 했습니다. 마크다운은 개발자에게 익숙하고 MDX는 여기에 JSX를 더해줄 수 있어서, 필요하다면 콘텐츠 안에 리액트 컴포넌트를 직접 넣어 확장할 수 있습니다.

여기서 우리는 MDX 파일을 어떻게 처리해야 할지 고민이 필요합니다.

## 왜 커스텀 MDX 컴파일러가 필요했을까?

Next.js의 기본 MDX 지원인 [@next/mdx](https://nextjs.org/docs/app/guides/mdx)는 훌륭하지만 커스터마이즈와 확장성 측면에서 제약이 많습니다.

[Contentlayer2](https://github.com/timlrx/contentlayer2)나 [Velite](https://velite.js.org)는 둘 다 로컬 파일 시스템의 콘텐츠를 애플리케이션에서 사용할 수 있는 데이터로 변환하는 데 사용되는 도구로, 정적 사이트 생성기(SSG)와 같은 최신 웹 프레임워크에서 콘텐츠를 처리하는 좋은 대안으로 사용됩니다.

다만, 애초에 이 블로그를 개발하는 계기가 **학습을 위한 목적**이 크기 때문에 이 부분도 **MDX 에코시스템을 적용해서 직접 구현**해보기로 했습니다.

## 개발 과정

`@codoodle/mdx`라는 이름의 패키지를 만들어 다음 기능들을 하나씩 구현해나갔습니다.

- **설정 파일 기반 유연한 구성**: `codoodle.config.js`를 통한 콘텐츠 타입, frontmatter 스키마, 출력 경로 등 설정

- **frontmatter 지원 및 타입 안전성 보장**: Zod를 활용한 런타임 타입 검증으로 frontmatter의 타입 안전성 보장

- **유연한 파일 구조 지원**: 글로빙 패턴을 사용해 다양한 디렉토리 구조의 MDX 파일들을 처리

- **파일 구조 기반 URL 슬러그 생성**: 파일 경로를 기반으로 자동으로 URL 슬러그 생성

- **콘텐츠 변환 기능**: transform 함수를 통해 콘텐츠와 메타데이터를 커스텀 처리 가능

- **각 콘텐츠를 React 컴포넌트로 컴파일**: MDX를 JSX 컴포넌트로 컴파일하여 React에서 직접 사용 가능

- **모든 콘텐츠를 하나의 인덱스 파일로 집약**: 타입 안전한 인덱스 파일 생성으로 편리한 import

- **개발 중 파일 변경에 대한 즉각적인 반응 (감시 모드)**: chokidar를 활용한 파일 감시로 증분 빌드 지원

- **빠른 빌드 성능 (증분 빌드, 병렬 처리 등)**: 캐시 기반 증분 처리와 동적 concurrency로 최적화된 성능

- **디렉토리 생성 캐싱**: 워치 모드에서 불필요한 디렉토리 생성 방지

- **사용하기 쉬운 명령줄 인터페이스 (CLI)**: `--watch`, `--clean` 등 다양한 옵션 제공

- **Next.js와의 원활한 통합**: JSX 컴포넌트 생성으로 Next.js 앱에서 바로 사용 가능

- **graceful shutdown**: SIGINT/SIGTERM 시그널 처리로 안전한 프로세스 종료

- **상세한 오류 메시지**: Zod 검증 오류와 파일 처리 오류에 대한 자세한 디버깅 정보 제공


### 기술 스택

- **`@mdx-js/mdx`**: MDX(Markdown + JSX) 파일을 React 컴포넌트로 컴파일하는 핵심 라이브러리. Remark/Rehype 기반으로 강력한 플러그인 생태계를 제공합니다. `outputFormat: "function-body"` 옵션으로 컴포넌트 함수를 생성할 수 있어 유연하게 사용할 수 있습니다.

- **`chokidar`**: Node.js용 크로스 플랫폼 파일 감시 라이브러리. 파일 시스템 이벤트를 효율적으로 감시하며, 개발 중 파일 변경에 즉각 반응하는 워치 모드를 구현하는 데 필수적입니다.

- **`globby`**: fast-glob 기반의 파일 매칭 라이브러리. 복잡한 글로빙 패턴을 사용해 특정 디렉토리에서 MDX 파일들을 찾는 데 사용합니다.

- **`gray-matter`**: Markdown 파일의 frontmatter를 파싱하는 라이브러리. YAML, JSON, TOML 등 다양한 포맷을 지원하며, MDX 파일에서 메타데이터를 추출하는 데 사용합니다.

- **`js-yaml`**: YAML 파서를 직접 제어하기 위해 사용. gray-matter의 기본 YAML 파서 대신 더 엄격한 JSON 스키마 검증을 위해 `js-yaml`을 사용합니다. `schema: yaml.JSON_SCHEMA` 옵션으로 JSON 호환 YAML만 허용합니다.

- **`p-map`**: Promise 기반 병렬 처리를 위한 유틸리티. 동적으로 결정된 concurrency 값(기본값: CPU 코어 수 x 2, 최소 2, 최대 12)으로 동시에 여러 파일을 처리하며, I/O 바운드 작업의 성능을 최적화합니다. concurrency 값은 각자의 환경에 맞게 설정으로 지정할 수 있습니다.

- **`picomatch`**: 고성능 글로빙 패턴 매칭 라이브러리. minimatch보다 빠르고 정확한 패턴 매칭을 제공합니다. 설정 파일의 글로빙 패턴과 실제 파일 경로를 매칭하는 데 사용됩니다.

- **`zod`**: TypeScript 우선 런타임 타입 검증 라이브러리. frontmatter의 타입 안전성을 보장하고, 개발 시점과 런타임 모두에서 타입 검증을 수행합니다.

### 3단계: Frontmatter 검증 시스템

Zod를 활용해 타입 안전한 frontmatter 검증을 구현했습니다:

```typescript
function createZodSchema(
  frontmatter?: Record<string, FrontmatterField>,
): ZodType {
  if (!frontmatter) return z.object({});

  const shape: Record<string, ZodType> = {};

  for (const [key, field] of Object.entries(frontmatter)) {
    let zodType: ZodType;

    switch (field.type) {
      case "string":
        zodType = z.string();
        break;
      case "date":
        zodType = z.iso.datetime();
        break;
      case "array":
        zodType = z.array(createZodSchema(field.fields));
        break;
      // ... 다른 타입들
    }

    if (!field.required) {
      zodType = zodType.optional();
    }

    shape[key] = zodType;
  }

  return z.object(shape);
}
```

### 4단계: MDX 컴파일레이션

`@mdx-js/mdx`를 사용해 MDX를 React 컴포넌트로 변환:

```typescript
async function processSingleFile(
  filePath: string,
): Promise<ProcessedContent | null> {
  const rawContent = await readFile(filePath, "utf-8");
  const { data, content } = matter(rawContent);

  // frontmatter 검증
  const validationSchema = createZodSchema(contentConfig.frontmatter);
  const parsedFrontmatter = validationSchema.parse(data);

  // MDX 컴파일
  const compiledMdx = await compile(content, compileOptions);

  // 최종 컴포넌트 코드 생성
  const generatedCode = `
const frontmatter = ${JSON.stringify(parsedFrontmatter, null, 2)};
export default {
  ...frontmatter,
  ContentComponent: (() => {
    ${compiledMdx}
  })().default,
};`;

  return processedItem;
}
```

## 워치 모드: 개발 경험 개선

개발 중 파일 변경에 즉각 반응하는 워치 모드를 구현했습니다.

### 초기 문제점

처음에는 파일이 변경될 때마다 모든 파일을 다시 처리했습니다:

```typescript
// 비효율적인 초기 구현
watcher.on("change", async (changedFile) => {
  const allContents = await processAllFiles(); // 😱 모든 파일 재처리
  await generateIndexFile(allContents);
});
```

### 최적화: 증분 처리

캐시를 활용한 증분 처리로 성능을 크게 개선했습니다:

```typescript
const processedContentsCache: Map<string, ProcessedContent> = new Map();

async function updateCacheAndIndex(
  filePath: string,
  operation: "add" | "update" | "remove",
) {
  const normalizedPath = resolve(filePath);

  if (operation === "remove") {
    // 캐시에서 제거하고 출력 파일도 삭제
    const existingEntry = Array.from(processedContentsCache.values()).find(
      (content) => resolve(content.filePath) === normalizedPath,
    );

    if (existingEntry) {
      processedContentsCache.delete(existingEntry.filePath);
      await rm(existingEntry.outFilePath, { force: true });
    }
  } else {
    // 변경된 파일만 다시 처리
    const processedContent = await processSingleFile(filePath, sourceDirectory);
    if (processedContent) {
      processedContentsCache.set(processedContent.filePath, processedContent);
    }
  }

  // 캐시 기반으로 인덱스 재생성 (빠름!)
  const allContents = Array.from(processedContentsCache.values());
  await generateIndexFile(allContents);
}
```

### Chokidar를 이용한 파일 감시

```typescript
const watcher = chokidar.watch("**/*.{md,mdx}", {
  cwd: sourceDirectory,
  ignored: (path, stats) =>
    !!stats?.isFile() && !path.endsWith(".md") && !path.endsWith(".mdx"),
  ignoreInitial: true,
  persistent: true,
});

watcher.on("change", async (changedFile) => {
  console.log(`🔄 File changed: ${changedFile}`);
  await updateCacheAndIndex(resolve(sourceDirectory, changedFile), "update");
});
```

## 성능 최적화

### 1. 디렉토리 생성 캐싱

```typescript
const createdDirectories = new Set<string>();

async function ensureDirectoryExists(dirPath: string) {
  if (isWatchMode && createdDirectories.has(dirPath)) {
    return; // 이미 생성된 디렉토리는 스킵
  }

  await mkdir(dirPath, { recursive: true });

  if (isWatchMode) {
    createdDirectories.add(dirPath);
  }
}
```

### 2. 병렬 처리

```typescript
// 동적으로 concurrency 결정 (I/O 바운드 작업에 최적화)
const defaultConcurrency = Math.min(Math.max(cpus().length * 2, 4), 16);
```

MDX 컴파일은 파일 I/O 위주의 작업이므로 CPU 코어 수의 2배 정도로 병렬 처리를 하는 것이 효율적입니다. 하지만 너무 많은 동시 작업은 메모리 사용량을 증가시키고 시스템을 불안정하게 만들 수 있으므로 상한선(16)을 두었습니다.

## 마무리하며

`@codoodle/mdx` 패키지를 만들면서 배운 점들:

### 기술적 성장

1. **TypeScript 활용**: Zod와 함께 런타임 타입 검증 구현
2. **Node.js 파일 시스템**: 효율적인 파일 처리와 캐싱 전략
3. **성능 최적화**: 증분 빌드와 병렬 처리 적용

### 개발 철학

1. **사용자 경험**: 개발자가 쓰기 편한 API 설계
2. **확장성**: 설정 파일을 통한 유연한 커스터마이징
3. **성능**: 워치 모드에서의 빠른 피드백 루프

결과적으로 블로그 개발이 훨씬 즐거워졌습니다. 파일을 수정하면 즉시 반영되고, 타입 안전성도 보장되니 안심하고 개발할 수 있습니다.

> 때로는 바퀴를 다시 발명하는 것도 의미가 있다는 걸 배웠습니다. 기존 솔루션이 완벽하지 않다면, 직접 만들어보는 과정에서 얻는 학습과 만족감이 충분히 가치 있으니까요.
